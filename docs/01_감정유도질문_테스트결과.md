## 1. 테스트 방법 2가지

**A. 시뮬레이션 테스트 (완료)** — 프롬프트의 AI 역할을 직접 맡아 10개 시나리오에 대한 답변을 생성한 뒤, `금지 사항 체크리스트` + `핵심 원칙 9개`를 코드로 옮긴 검증기(`tests/validator.py`)로 자동 채점했다. API 키 없이 지금 바로 결과를 확인할 수 있는 방식이다.

**B. 실제 API 회귀 테스트 (스크립트 제공, 팀에서 실행 필요)** — `seenears_ai_pipeline_README.md` 기준 실제 서비스는 Gemini 2.5 Flash를 쓰므로, 동일 모델에 실제로 프롬프트를 태워 검증하는 스크립트를 `tests/run_gemini_test.py`에 만들어 두었다. `GEMINI_API_KEY`만 설정하면 실행된다. 시뮬레이션은 "설계가 논리적으로 맞는가"를, API 테스트는 "실제 모델이 규칙을 지키는가"를 검증하므로 최종심사 전 둘 다 돌려보는 것을 권장한다.

## 2. 시뮬레이션 테스트 결과 (10건)

검증 항목: 문장수(최대 2), 길이(25~45자 권장), 금지어(진단명·위험표현·"왜/걱정" 등), 열린질문 여부, `recent_questions` 중복도, `digital_grade C` 난이도.

| ID | 시나리오 | 생성된 질문 | 판정 |
|---|---|---|---|
| TC1 | sunny + 손녀 방문 맥락 + A등급 | "요즘 손녀 만나서 제일 즐거우셨던 순간은 언제였어요?" | PASS |
| TC2 | sunny + 맥락 없음 + B등급 | "오늘 하루 중에서 제일 마음에 남는 순간은 뭐였어요?" | PASS |
| TC3 | cloudy + 화투모임(최근 질문에 이미 등장) + A등급 | "오늘은 마음이 애매한 하루였나 봐요. 오늘 하루는 어떻게 보내셨어요?" | PASS |
| TC4 | cloudy + 맥락 없음 + C등급(쉬운 문장 요구) | "오늘 하루는 어떠셨어요?" | PASS |
| TC5 | rainy + 맥락 없음 + A등급 | "오늘은 편하게, 그냥 생각나는 대로 들려주시겠어요?" | PASS |
| TC6 | rainy 3일 연속 + B등급 (톤 과잉 심각화 방지) | "오늘도 편하게, 하고 싶은 이야기만 들려주세요." | PASS |
| TC7 | sunny + 최근 5일 동일질문 반복 (다양성 스트레스) | "오늘처럼 맑은 날엔 어떤 게 제일 먼저 떠오르세요?" | WARN (경미) |
| TC8 | rainy + 배우자 기일 최근 언급 (민감소재) | "오늘은 편하게, 마음에 있는 이야기 아무거나 들려주시겠어요?" | PASS |
| TC9 | sunny + 손녀 맥락 + 일본어 | 「最近お孫さんに会って、一番嬉しかった瞬間はいつでしたか?」 | PASS |
| TC10 | cloudy + 건강/경제 축 반복 → 축 전환 테스트 | "요즘 하루 중에 마음이 제일 편했던 시간은 언제였어요?" | PASS |

**9/10 PASS, 1/10 WARN(경미)**. TC7의 WARN은 FAIL 기준(유사도 0.6 이상)에 못 미치는 0.4 수준의 낮은 경고로, "오늘"이라는 흔한 단어가 겹친 정도다. 실사용에는 문제없지만, `recent_questions`가 5일 내내 완전히 동일한 극단적 상황에서는 다양성 로직에 참고용 축 목록([참고: 주제 축])을 더 적극적으로 활용하도록 프롬프트에 한 문장을 보강하는 것을 고려할 만하다.

### 눈여겨볼 시나리오

- **TC6 (3일 연속 비)**: 원칙대로 "위험 판단은 이 프롬프트의 역할이 아니다"를 지켜, 3일 연속임에도 질문 톤이 심각해지지 않고 다정함만 유지됨을 확인. Rule-based Triage(별도 파이프라인)와 역할 분리가 실제로 작동하는 설계.
- **TC8 (배우자 기일 언급 + 비)**: "recent_context를 자연스럽게 이어받는다"는 원칙 5와 "rainy는 자세한 설명을 요구하지 않는다"는 톤 규칙이 충돌할 수 있는 조합이었으나, 시뮬레이션에서는 rainy의 저압력 원칙이 우선되어 기일을 직접 언급하지 않고 여지만 주는 방향으로 자연스럽게 처리됨. 다만 이 우선순위(민감 소재일 때 rainy 규칙이 context 반영보다 우선한다)가 시스템 프롬프트에 명시적으로 적혀 있지는 않음 — 실제 모델이 항상 이렇게 판단한다는 보장은 없으므로 아래 개선 제안 참고.

## 3. 문서 자체 few-shot 예시 검증 (발견 후 수정 완료)

기존 `## 예시 (Few-shot)` 섹션의 예시도 같은 검증기로 돌려본 결과, 규칙과 예시가 어긋나는 부분을 발견했다.

| 예시 | 수정 전 글자수 | 규칙(25~45자) 대비 | 조치 |
|---|---|---|---|
| 1) sunny/맥락 있음 | 52자 | 초과 (약 15%) | 39자로 단축 완료 |
| 2) cloudy/맥락 없음 | 51자 | 초과 (약 13%) | 38자로 단축 완료 |
| 3) rainy/3일 연속 | 35자 | 정상 | 유지 |
| 4) sunny(日本語) | 44자 | 정상 | 유지 |

**이슈**: 원칙 8은 "6~10초, 약 25~45자, 최대 2문장"이라고 못박아 두었는데, 정작 문서가 제시하는 few-shot 예시 1·2번은 그 상한을 13~15% 넘었다. 개발자가 이 예시를 참고해 few-shot을 그대로 재사용하면 프롬프트 스스로 정한 규칙을 프롬프트가 어기는 모순이 생길 수 있었다. `01_감정유도질문_프롬프트.md`의 예시 1·2번을 각각 39자·38자로 다듬어 이미 반영해 두었다.

## 4. 프롬프트 개선 제안 (선택사항)

아래 2가지는 아직 미반영 상태로, 팀 논의 후 적용 여부를 결정하면 된다.

1. **민감 소재 우선순위 명문화**: "recent_context에 사별·기일 등 민감한 사건이 있고 동시에 weather=rainy인 경우, 원칙 5(맥락 이어받기)보다 rainy의 저압력 원칙을 우선한다"는 문장을 [날씨별 톤 분기]의 rainy 항목에 한 줄 추가하면, 모델마다 판단이 갈릴 수 있는 지점을 없앨 수 있다.
2. **다양성 로직 보강**: recent_questions가 동일 문장으로 반복될 경우 [참고: 주제 축] 목록에서 아직 다루지 않은 축을 우선 선택하라는 지시를 조금 더 명시적으로 추가.

(길이 규칙-예시 정합화는 위 3절에서 이미 수정 완료)

## 5. 실제 API 테스트 실행 방법 (팀 개발 담당용)

```bash
cd AI_프롬프트/tests
export GEMINI_API_KEY="발급받은_키"
pip install requests --break-system-packages   # 이미 설치돼 있으면 생략
python3 run_gemini_test.py
```

- `test_inputs.json`: 위 TC1~TC10과 동일한 10개 입력 시나리오
- `validator.py`: 시뮬레이션과 동일한 채점 로직 (재사용)
- 실행 후 `results.csv`에 케이스별 실제 모델 응답과 판정이 저장되어, 프롬프트 수정 전후 비교(회귀 테스트)에 그대로 재사용 가능

## 결론

10개 시나리오 기준 프롬프트는 설계 의도대로 안정적으로 동작하는 것으로 시뮬레이션에서 확인됐다(9 PASS / 1 경미한 WARN). 문서 자체의 few-shot 예시가 스스로 정한 길이 규칙을 벗어나 있던 부분은 이번에 바로 수정했고, 민감 소재 처리 우선순위 명문화는 선택적 개선사항으로 남겨두었다. 최종 확인은 `run_gemini_test.py`로 실제 Gemini 응답을 받아본 뒤 결정할 것을 권장한다.
