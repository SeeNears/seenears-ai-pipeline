# See-Nears AI 에이전트 통합 설계 문서

> 역할: [프롬프트 ①: 감정유도 질문]과 [프롬프트 ②: AI 편지 생성]을 하나의 에이전트 파이프라인으로 통합 기술한다.
> 이 문서는 두 프롬프트를 개별 부품이 아니라 "매일 저녁 질문 → 다음 날 아침 편지"로 이어지는 하나의 상태 기계(state machine)로 읽히도록 설계·재구성한 마스터 문서다.
> 버전: v1 · 작성일: 2026-07-04 · 기준 문서: See-Nears_프로젝트_마스터문서_v3, 01_감정유도질문_프롬프트.md, 02_AI편지_프롬프트.md

---

## 0. 한눈에 보기 — 심사위원용 요약 (복지 · 개발 공통)

See-Nears의 AI는 하나의 에이전트이지만 매일 두 번, 서로 다른 시점에 호출된다.

1. **저녁**: 어르신이 오늘의 기분을 날씨(☀️/☁️/☔)로 고르면, 에이전트는 [Stage 1] 프롬프트로 질문을 딱 1개 생성한다. 어르신은 이 질문에 30초 남짓 음성으로 답한다.
2. **다음 날 아침**: 에이전트는 그 음성(STT 텍스트)과 어제의 질문·날씨를 입력으로 받아 [Stage 2] 프롬프트로 3문장짜리 편지를 생성한다. 편지는 어르신의 우편함(감정 캘린더)에 도착한다.

두 프롬프트는 별개의 기능이 아니라 **하나의 정체성(말동무 AI)과 하나의 원칙 세트(진단하지 않기·판단은 분리하기·상대의 표현을 존중하기)를 공유하는 앞뒤 단계**다. Stage 1의 출력(JSON)이 Stage 2의 입력 일부가 되는 구조로, 두 단계가 어긋나면(예: 질문에서는 다정했는데 편지에서 훈계조가 되면) 어르신이 서비스 전체를 하나의 인격으로 신뢰하기 어려워진다. 이 문서는 그 일관성을 보장하기 위해 두 프롬프트에 공통되는 규칙을 한 곳에 모으고, 각 프롬프트 고유의 로직은 원문 그대로 남겨 개발/QA가 참조할 수 있게 한다.

## 1. 에이전트 정체성 (Persona) — 두 Stage 공통

| 항목 | 정의 |
|---|---|
| 이름/역할 | "See-Nears"의 말동무 AI — 매일 안부를 궁금해하는 동네 말벗 |
| 아닌 것 | 상담사 아님, 조사관 아님, 복지사 아님, 진단 도구 아님 |
| 유일한 목적 | (Stage 1) 30초 음성 응답을 이끌어내는 것 / (Stage 2) 오늘 기분을 있는 그대로 받아들이고 아주 작은 힘으로 내일을 시작하게 돕는 것 |
| 핵심 태도 | "나쁜 기분이 나쁜 것만은 아니다" — 기분을 고치거나 없애야 할 문제로 다루지 않는다 |
| 어르신 관점 | 돌봄을 받는 수동적 대상이 아니라 매일 감정을 표현하는 능동적 주체 |
| 위험판단 관계 | Stage 1·Stage 2 모두 위험/위기 판단을 **직접 하지 않는다.** 감지·기록만 하고 사람의 개입 여부 판단은 별도 파이프라인(트리아지 엔진)이 담당한다 |

이 표는 [01_감정유도질문_프롬프트.md](./01_감정유도질문_프롬프트.md)와 [02_AI편지_프롬프트.md](./02_AI편지_프롬프트.md) SYSTEM PROMPT 도입부에 각각 반복 서술된 정체성 규정을 하나로 합친 것이다. 두 프롬프트를 수정할 때는 이 표부터 먼저 갱신하고, 두 파일에 동일하게 반영한다.

## 2. 전체 파이프라인 아키텍처

```
[저녁]                                              [익일 아침]
어르신 날씨 선택(☀️/☁️/☔)                                  │
        │                                                  │
        ▼                                                  │
┌───────────────────────┐                                  │
│  STAGE 1               │                                  │
│  감정유도 질문 생성      │                                  │
│  (01_감정유도질문_프롬프트) │                                  │
└──────────┬────────────┘                                  │
           │ JSON: {question, weather_tone,                │
           │        references_context, language}          │
           ▼                                                │
   어르신 음성 응답 (30초) ──▶ STT ──▶ transcript            │
           │                                                │
           └────────────────────────────────────────────────┘
                                        │
                                        ▼
                          ┌───────────────────────┐
                          │  STAGE 2               │
                          │  AI 편지 생성           │
                          │  (02_AI편지_프롬프트)     │
                          └──────────┬────────────┘
                                     │ JSON: {letter_text, quoted_phrase,
                                     │  emotion_label, basic_emotion,
                                     │  keyword, internal_risk_flag, language}
                                     ▼
                     우편함(감정 캘린더)에 편지 도착
                     + internal_risk_flag는 트리아지 엔진으로만 전달
                     (어르신·가족에게는 절대 미노출)
```

**설계 포인트**
- 두 Stage는 반드시 순차적이다. Stage 2는 Stage 1의 `question`(question_asked)과 어르신의 실제 응답(transcript)이 있어야 성립한다 — Stage 2 단독 호출은 정의되지 않음.
- `weather`는 두 Stage 모두에 독립 입력되며, 두 단계의 톤이 어긋나지 않도록 동일한 값을 그대로 전달해야 한다(질문은 맑음 톤인데 편지가 비 톤이 되는 등의 불일치 방지).
- `internal_risk_flag`(Stage 2 산출)와 Stage 1이 참고하는 `recent_questions`/`recent_context`는 같은 사용자 로그 저장소에서 순환 참조된다 — 다음 날 저녁 Stage 1 호출 시 어제 편지 요약이 `recent_context`로 들어갈 수 있다는 뜻.
- 위험 신호 감지(Stage 2의 `internal_risk_flag` 상향)와 [seenears_ai_pipeline_README.md](../seenears_ai_pipeline_README.md)의 Rule-based Triage(3일 연속 비, 2일 이상 미접속 등)는 별도 레이어다. 이 문서의 두 프롬프트는 "매일의 말벗" 역할만 하고, 위기 판정은 트리아지 엔진이 전담한다는 원칙을 재확인한다.

## 3. Stage 1 — 감정유도 질문 생성

전체 SYSTEM PROMPT, few-shot 예시, [입력]/[출력] 스키마는 [01_감정유도질문_프롬프트.md](./01_감정유도질문_프롬프트.md)에 원문 그대로 유지한다(중복 방지). 이 절에서는 에이전트 전체 관점에서 알아야 할 핵심만 요약한다.

- **입력**: `weather`, `language`, `recent_context`(선택), `digital_grade`(선택, A/B/C), `recent_questions`(선택, 최근 5일)
- **출력(JSON)**: `question`, `weather_tone`, `references_context`, `language`
- **핵심 원칙 요지**: 질문 1개만, 감정 이름표를 AI가 먼저 붙이지 않음, 열린 질문만, 진단명·위험 표현 금지, 6~10초 분량, 최근 5일과 소재 중복 금지
- **날씨별 톤 분기**: sunny=긍정 회상 유도 / cloudy=압력 없는 수용 / rainy=최저압력, 3일 연속이어도 표현을 심각하게 바꾸지 않음
- **학술적 근거 5축**: Affect Labeling(Lieberman), 사회적 고립의 건강위험(Holt-Lunstad), 긍정 회상(Seligman), 개방형 질문의 신뢰관계 우위(개방형 질문 임상비교), 표현적 disclosure(Pennebaker) — 상세는 §6 통합 매핑표 참고

## 4. Stage 2 — AI 편지 생성

전체 SYSTEM PROMPT, few-shot 예시, [입력]/[출력] 스키마는 [02_AI편지_프롬프트.md](./02_AI편지_프롬프트.md)에 원문 그대로 유지한다(중복 방지). 이 절에서는 에이전트 전체 관점에서 알아야 할 핵심만 요약한다.

- **입력**: `weather`, `transcript`, `question_asked`(선택, Stage 1 출력), `language`, `user_code`(내부 로깅 전용), `recent_letters_summary`(선택)
- **출력(JSON)**: `letter_text`(정확히 3문장), `quoted_phrase`, `emotion_label`, `basic_emotion`, `keyword`, `internal_risk_flag`, `language`
- **편지 구조**: 1문장 공감(Affect Labeling) → 2문장 기억(Positive Reminiscence/버텨낸 부분 짚기) → 3문장 행동제안(Behavioral Activation, 초대형 어미)
- **절대 금지**: 충고·지시형 어미, 비난 뉘앙스, 진단명·의학용어, 내부 판정 노출 표현, 완곡표현 반박, 사실 창작, 개인정보 노출, 이모지·물음표 남발
- **이론적 근거 4축**: Affect Labeling(Lieberman) / 긍정 회상(Seligman) / 자기연민(Neff) / 행동활성화(Martell) — 상세는 §6 통합 매핑표 참고
- **`internal_risk_flag`의 위치**: 어르신·가족 비노출, 실시간 알림 미사용, 파이프라인 내부 로그·후속 검토 전용. Stage 1에는 없는 값으로, Stage 2에서 새로 생성되어 트리아지 엔진으로 흘러간다(§2 아키텍처 참고).

## 5. Stage 간 데이터 스키마 연결

| Stage 1 산출 필드 | Stage 2 입력 매핑 | 비고 |
|---|---|---|
| `question` | `question_asked` | 편지 1문장(공감)이 "무엇에 대한 응답인지" 맥락을 잡을 때 참고 |
| `weather_tone` | (원본 `weather` 값 재사용) | Stage 1·2 모두 동일한 `weather` 원본 입력을 각자 받는 것이 원칙 — `weather_tone`은 검증용 |
| `language` | `language` | 한 세션 내 동일 언어 유지 필수 |
| `references_context` | (직접 미전달) | Stage 1이 맥락을 참조했는지 여부 — 로그 분석·품질 모니터링용 |
| (음성 응답) | `transcript` | Stage 1의 `question`에 대한 STT 결과. Stage 2 유일의 필수 신규 입력 |
| (전일 요약, 어제 편지 loop) | Stage 1의 `recent_context` | Stage 2 편지의 `keyword`/소재가 다음 날 Stage 1 맥락으로 순환 |
| `internal_risk_flag`, `basic_emotion` | Stage 1의 `recent_questions` 다양성 로직에 간접 반영 가능(향후 고도화 항목, §10) | 현재는 직접 연결 안 됨 — 결선 개발 기간 개선 후보 |

이 표가 두 문서를 "한 문서"로 만드는 핵심 근거다 — Stage 1과 Stage 2는 각자 독립 프롬프트지만, 실제로는 이 표의 필드 매핑을 통해 하나의 대화 세션 상태를 주고받는다.

## 6. 공통 설계 원칙 ↔ 학술 근거 통합 매핑

| 설계 원칙 | 적용 Stage | 근거 |
|---|---|---|
| 감정 이름표는 AI가 먼저 붙이지 않는다 / 스스로 말한 감정만 되짚는다 | Stage 1 (원칙 3) · Stage 2 (1문장 공감) | Lieberman et al., 2007 — Affect Labeling; Torre & Lieberman, 2018 |
| 열린 질문·진단적 질문 회피 | Stage 1 (원칙 3·4) | 개방형 질문 임상 비교연구 (PRIME-MD 대비) |
| 좋은 기억을 구체적으로 다시 음미 | Stage 1 (sunny 톤 분기) · Stage 2 (2문장 기억) | Seligman 긍정심리/PERMA, 회상요법 메타분석 |
| 힘든 날은 자책이 아닌 수용의 언어 | Stage 2 (2문장, cloudy/rainy) | Neff, 자기연민(Self-Compassion) |
| 아주 작은 행동은 지시가 아닌 초대로 | Stage 2 (3문장 행동제안) | Martell, 행동활성화(Behavioral Activation) |
| 짧게라도 말로 표현하는 행위 자체의 효과 | Stage 1 (30초 음성 유도 목적) | Pennebaker, 2018 — Expressive Disclosure |
| 사회적 고립은 건강 위험요인 — 문제정의의 근거 | 서비스 전체 (Stage 1·2 공통 배경) | Holt-Lunstad et al., 2015 |
| AI와의 대화형 상호작용이 실제로 고립감을 낮춘다 | 서비스 모델 전체 근거 | I-CONECT RCT, BOCCO emo RCT |
| 사투리·완곡표현은 지적하지 않고 액면 그대로 수용, 톤만 조절 | Stage 1 (원칙 6) · Stage 2 (분석절차 1, 절대금지) | AI Hub 노인 발화 데이터 검증 결과(§7) |
| 위험판단은 이 프롬프트의 역할이 아니다 — 별도 파이프라인 위임 | Stage 1 (원칙 7) · Stage 2 (분석절차 3, `internal_risk_flag`) | 초기 기획 피벗 근거 (중간심사_필수섹션_초안.md 이슈 1) |

## 7. 공통 데이터 거버넌스 (AI Hub 데이터셋)

두 프롬프트 문서에 각각 기재된 데이터 출처·라이선스·검증 결과를 통합한다. 상세 수치·인용 예시는 각 원문 문서를 참조하고, 여기서는 팀 전체가 지켜야 할 공통 규칙만 정리한다.

| 데이터셋 | Stage 1 활용 | Stage 2 활용 |
|---|---|---|
| ★노년층 대상 감성 분류 모델 (AI Hub, dataSetSn=453) | 주제 축(건강/경제/가족/사별/외로움/역할상실) 실증 근거 | `basic_emotion` 6종 분류체계 1차 근거, 공감 화법 few-shot |
| 감성 대화 말뭉치 (AI Hub, 7978) | `recent_questions` 다양성 로직 보조 근거 | 완곡표현·관용적 과장 구분 규칙 고도화 |
| 연령대별 특징적 발화(사투리·속어) 음성 데이터 | 원칙 6 검증용 실 발화 샘플 | `quoted_phrase` 자연스러움 검증 |
| 60세 이상 자연어 자유대화 데이터 | 질문 길이·종결어미 캘리브레이션 | transcript 문체 캘리브레이션 |

**공통 컴플라이언스 규칙**
- 영리·비영리 연구개발 목적 모두 사용 가능하나 학습용 한정, NIA 출처 표기 의무, 제3자 재배포 금지
- **국외 반출·국외 이용은 NIA와 별도 합의 필요** — 오사카 실증(10/19~23) 전 정화민 멘토를 통해 반드시 재확인
- "노년층 대상 감성 분류 모델"은 내국인만 신청 가능, 다운로드(본인확인·이용목적 기재·약관 동의)는 팀(윤솔지)이 직접 진행
- **⚠ 실 데이터 원문 문장(train.csv 인용 등)은 심사위원 PPT·공개 GitHub 등 외부 제출자료에 그대로 싣지 않는다.** 축약된 인사이트만 사용하고, 다운로드 폴더(`AI_프롬프트/노년층 대상 감성 분류 모델/`)는 공개 저장소에 커밋하지 않는다
- **주의 발견 공통 반영**: 원본 데이터의 시스템 응답 일부가 진단명("치매", "우울증")을 그대로 따라 말하는 경우가 있음 — See-Nears 두 프롬프트 모두 이보다 엄격한 기준(진단명 절대 미언급)을 적용하므로, 이 데이터를 few-shot으로 차용할 때는 진단명 부분을 감정 표현으로 반드시 치환

## 8. 통합 금지사항 체크리스트 (개발/QA용)

**Stage 1 (질문 생성)**
- [ ] 질문이 2개 이상 포함되지 않았는가
- [ ] "왜/무엇 때문에/걱정" 등 원인을 캐묻는 표현이 없는가
- [ ] 진단명·위험 관련 단어가 없는가
- [ ] Yes/No로 끝나는 폐쇄형 질문이 아닌가
- [ ] 이전 5일 질문과 소재가 중복되지 않는가

**Stage 2 (편지 생성)**
- [ ] 정확히 3문장인가
- [ ] 지시형 어미가 아닌 초대형 어미로 끝나는가
- [ ] 진단명·의학 용어가 없는가
- [ ] "위험/신호/알림" 등 내부 판정 노출 표현이 없는가
- [ ] transcript에 없는 사실을 지어내지 않았는가
- [ ] user_code·실명 등 개인정보가 노출되지 않았는가
- [ ] 완곡 표현을 지적하거나 반박하지 않았는가

**에이전트 전체(교차 검증)**
- [ ] Stage 1의 `weather`와 Stage 2에 전달된 `weather`가 동일한가
- [ ] Stage 1·2의 어조가 같은 인격(다정한 말벗)으로 일관되는가 — 질문은 다정한데 편지가 사무적인 등 불일치 없는가
- [ ] `internal_risk_flag`가 편지 문구·질문 문구 어디에도 직·간접적으로 드러나지 않았는가
- [ ] 언어(`language`) 파라미터가 세션 내내 ko/ja 중 하나로 고정되어 있는가

## 9. 언어 지원 (ko/ja) 공통 규칙

- 두 Stage 모두 `language: "ko" | "ja"` 파라미터 하나로 전환되며, 시스템 프롬프트 본문·출력 스키마 구조는 언어와 무관하게 동일하다
- 위험 키워드·완곡표현 판단 로직은 언어별로 별도 구성: 한국어는 노인 발화 패턴/사투리/완곡 표현, 일본어는 현지 멘토(키쿠치 진, 나카무라 쇼헤이) 자문으로 구성
- 오사카 실증(10/19~23) 전 일본어 표현 검증을 Stage 1·2 모두에 대해 완료해야 함 (결선 개발 기간 계획, §10)

---

## 10. 향후 고도화 로드맵 (결선 개발 기간 7/8~8/17 연계)

- Stage 1·2 공통: 3요소(공감·기억·행동제안) 자연스러움 개선, 어르신 원문 표현 인용 로직 강화
- Stage 1: `recent_letters_summary`(Stage 2 산출)를 `recent_context`에 구조적으로 연결해 다음 날 질문의 연속성 로직 정식화 (현재 §5에서 "간접 반영"으로 표기된 부분의 고도화)
- Stage 2: "도움이 되었어요" 피드백 버튼 데이터를 편지 품질 개선 루프에 연결
- 공통: 20~30건 테스트 케이스 기반 검증 프로세스를 Stage 1·2 동시 실행 시나리오로 확장(현재는 각 프롬프트 개별 테스트 중심)
- 일본어 지원 완성 및 현지 멘토 검증 (§9)
- 중장기: 데이터 축적 후 Vertex AI SFT 파인튜닝 → 상용화 단계 Gemma 4 온디바이스 전환(완전 로컬 처리, 해외 규제 대응력 강화)
